# Remnawave Subscription Middleware

![status: beta](https://img.shields.io/badge/status-beta-e2b341)
![PHP 8.1+](https://img.shields.io/badge/PHP-8.1%2B-7c9cff)
![docker: ghcr.io](https://img.shields.io/badge/docker-ghcr.io-2496ed)

![Превью админки — вкладка «Пользователи»](docs/preview.jpg)

Прослойка для подписок [Remnawave](https://remna.st): встаёт перед панелью и на лету правит выдачу подписки — заголовки под приложения, заглушки для заблокированных устройств, мягкое истечение («грейс-сквад»). Основной сценарий — зеркало для России: клиент ходит на ваш РФ-домен, а прослойка проксирует запрос на origin-домен панели. В комплекте — веб-админка поверх API панели и пересылка вебхуков на несколько адресов.

💬 **Чат проекта:** https://t.me/+GTkYbwX3alg0ZGEy

> [!WARNING]
> **Проект в стадии активной разработки (beta).** Возможны ошибки, часть поведения
> ещё обкатывается. Перед установкой сделайте бэкап панели.
>
> Из всех функций в живую панель пишет только функция «грейс-сквад» — и она по
> умолчанию выключена. Что именно и когда меняется — в разделе
> [«Может ли прослойка навредить»](#может-ли-прослойка-навредить-панели-и-пользователям).

## ⚡ Быстрый старт

Прослойка ставится перед панелью Remnawave. Два способа установки:

**Рядом с панелью (Docker, рекомендуется):**

```bash
sudo apt update && sudo apt install -y git
sudo git clone https://github.com/Mrvibecodic/remnawave-subscription-middleware \
    /opt/remnawave-subscription-middleware
cd /opt/remnawave-subscription-middleware
sudo bash install.sh        # выбрать «2) Рядом с панелью — Docker»
```

**Отдельный сервер (файлами):** те же команды, но в `install.sh` выберите «1) Отдельный сервер».

Отдельный сервер можно поднять и на Docker — образ универсальный: запустите контейнер своим `docker-compose` (TLS и домен — внешним reverse-proxy перед ним) и в мастере админки выберите режим «зеркало». Через `install.sh` этот путь не ставится — только вручную.

Дальше откройте `https://<домен>/admin/` и пройдите мастер первого запуска. Подробно — раздел [Установка](#установка) и пошаговый [INSTALL.md](INSTALL.md).

> [!TIP]
> Адрес админки — со слешем на конце: `https://<домен>/admin/`.

Прослойка работает в двух режимах:

- **Зеркало** — проксирует домен подписки панели (основной РФ-сценарий).
- **Основная подписка** — сама отдаёт конфиги с `/api/sub` и рисует страницу подписки.

## Зачем это нужно

Панель Remnawave обычно живёт на зарубежном origin за Cloudflare. Из России
такой адрес часто открывается нестабильно, и **подписки у клиентов перестают
обновляться** — приложение не может достучаться до origin. Прослойка решает это:
клиент ходит на РФ-зеркало, а уже зеркало со своей стороны проксирует запрос на
origin (часто доступный с сервера, даже если у клиента он заблокирован).

Попутно прослойка добавляет удобства на стороне зеркала: точечную блокировку
устройств с понятным сообщением, «грейс» вместо жёсткого отключения,
переопределение заголовков под конкретные клиенты и единое окно для саппорта.

## Возможности

Прослойка не заменяет панель — она стоит **перед** ней и берёт на себя то, что удобнее делать на стороне РФ-зеркала.

- **Зеркало подписок** — проксирует запросы подписки с РФ-домена на origin панели. Надёжное обновление подписок у клиентов из России.
- **Грейс-сквад для истёкших** — вместо жёсткого отключения переносит истёкшего в ограниченный сквад на заданный срок и возвращает обратно при оплате. По умолчанию выключено.
- **HWID-блокировка устройств** — точечно блокирует конкретное устройство по его HWID: оно видит заглушку с вашим текстом вместо конфига. Просмотр и удаление устройств — из админки.
- **HWID из User-Agent** — для клиентов, которые не умеют слать HTTP-заголовки, но позволяют менять User-Agent (v2rayNG, Clash): прослойка берёт данные об устройстве из строки User-Agent.
- **Правила ответа по приложению** — подмена заголовков подписки под конкретный клиент (profile-title, announce, интервал обновления и т.д.) по User-Agent и ОС.
- **Доп. конфиги по сквадам (бета)** — добавляет в подписку конфиги WireGuard / AmneziaWG / VLESS по внутреннему скваду, подстраивая формат под клиент.
- **Пул WG/AWG-конфигов (бета)** — раздаёт готовые `.conf` из загруженного пула, закрепляя за подписчиком или устройством отдельный конфиг (один WG-ключ нельзя делить между устройствами).
- **Слияние двух подписок** — узлы второй подписки подмешиваются в тело основной: клиент получает одну ссылку, серверы из обеих лежат вместе.
- **Обновление с GitHub** — встроенное обновление по коммитам: тянет только изменённые файлы, делает бэкап с откатом. Пункт меню подсвечивается, когда есть что обновить.
- **Пересылка вебхуков (тройник)** — входящий вебхук панели можно разослать на несколько адресов, переподписав каждого его секретом.
- **Веб-админка** поверх API панели: пользователи со ссылками подписки, устройства HWID, оверрайды, логи, брендинг. Настройки сохраняются автоматически.
- **Брендинг автоматически** подтягивается из панели (имя и логотип), с ручным переопределением при необходимости.
- **Маскировка с выбором дизайна** — на не-подписочные запросы отдаётся нейтральная страница входа вместо голого прокси; её вид выбирается в «Брендинге».
- **Чат поддержки на странице-заглушке** — встроенный чат с переотправкой в Telegram и вебхук-fallback; оператор отвечает из админки, Telegram или вебхуком.
- **Мониторинг нагрузки** — вкладка «О системе»: версия PHP/ОС/БД, график запросов (отделяет реальные обновления подписки от сканеров), детектор аномальных пиков.

## Установка

Три способа установки (первые два ставит `install.sh`, третий — вручную):

1. **Рядом с панелью, Docker (рекомендуется)** — контейнер прослойки встаёт перед контейнером `subscription-page` панели: на пути клиента добавляет свои функции, а саму страницу подписки в браузере проксирует на него же. Обновление — одной командой `docker compose pull`.
2. **Отдельный сервер (файлами)** — классическое зеркало: nginx + PHP-FPM + TLS на своём домене, проксирование origin-домена подписки.
3. **Отдельный сервер на Docker (вручную)** — тот же образ, что в варианте 1, но запускается сам по себе на отдельном сервере. `install.sh` этот путь не ставит, настройка ручная (см. ниже).

> 📘 **Пошаговая инструкция — [INSTALL.md](INSTALL.md):** Docker-установка рядом с панелью (правка nginx панели, перевод домена подписки на прослойку) и установка на отдельный сервер. На эту же страницу ссылается вывод `install.sh`.

### Вариант 1. Рядом с панелью (Docker)

Панель и её reverse-proxy уже работают, домен подписки обслуживает контейнер `subscription-page`. Прослойка встаёт **перед** ним:

```bash
sudo apt update && sudo apt install -y git
sudo git clone https://github.com/Mrvibecodic/remnawave-subscription-middleware \
    /opt/remnawave-subscription-middleware
cd /opt/remnawave-subscription-middleware
sudo bash install.sh        # выбрать «2) Рядом с панелью — Docker»
```

Установщик спросит домен подписки, имя docker-сети панели, внутренние URL панели и контейнера `subscription-page`, тег образа (`latest` — стабильный, или `dev` — тестовый; см. [docs/docker-image-tag.md](docs/docker-image-tag.md)), создаст `docker-compose.yml`, скачает образ из GHCR и поднимет контейнер. Останется одной строкой в nginx панели перевести домен подписки с контейнера `subscription-page` на прослойку — все шаги в **[INSTALL.md](INSTALL.md)**. Контейнер `subscription-page` останавливать не нужно; данные (`config.php`, БД) живут в volume и переживают `docker pull`.

### Вариант 2. Отдельный сервер (файлами)

На чистом **сервере** (Ubuntu 22.04+/Debian 12+) ставится **актуальный nginx (из официального репозитория nginx.org) +
PHP-FPM + SQLite** (по умолчанию; опционально MySQL/MariaDB). Клонируйте репозиторий в `/opt` и запустите
установщик:

> [!IMPORTANT]
> Этот вариант рассчитан на **чистый сервер**. nginx ставится из репозитория
> nginx.org, поэтому если на сервере **уже стоит nginx**, установщик предложит
> сначала удалить его (вместе с каталогом `/etc/nginx`). Перед удалением он делает
> резервную копию `/etc/nginx` в `/root/` и спрашивает подтверждение дважды, но
> **другие сайты на этом nginx перестанут работать**. Если nginx уже обслуживает
> другие проекты — ставьте прослойку на отдельный сервер или вручную (см. раздел
> про шаред-хостинг).

```bash
sudo apt update && sudo apt install -y git
sudo git clone https://github.com/Mrvibecodic/remnawave-subscription-middleware \
    /opt/remnawave-subscription-middleware
cd /opt/remnawave-subscription-middleware
sudo bash install.sh        # выбрать «1) Отдельный сервер»
```

На минимальных образах Ubuntu/Debian git не предустановлен — первая строка ставит
его. Папку создавать не нужно — `git clone` создаёт её сам; `sudo` обязателен,
потому что запись в `/opt` доступна только root.

Установщик сам:

- доставит зависимости, если их нет (актуальный nginx из nginx.org, php-fpm, php-sqlite3, php-mysql, certbot);
- создаст БД (SQLite-файл или MariaDB — по выбору);
- развернёт файлы в `/opt/remnawave-subscription-middleware`;
- выпустит TLS-сертификат;
- пропишет **полный конфиг nginx**: вебхук `/webhook.php`, обработку запросов
  подписки, отдачу статики, редирект 80→443 и закрытие служебных файлов
  (`config.php`, `lib/`, `schema.sql` и т.п.) — всё прямо в nginx, потому что на
  чистом nginx `.htaccess` не работает.

Скрипт спросит:

- **домен прослойки** — он же домен зеркала подписок (один домен);
- **origin-домен** подписки панели (напр. `sub.example.com`);
- **тип БД**: SQLite (по умолчанию — ничего не ставится) или MySQL/MariaDB
  (установщик сам поставит лёгкую MariaDB и создаст базу со случайными именем,
  пользователем и паролем);
- **способ выпуска сертификата** на выбор:
  - **HTTP-01** — валидация по 80 порту (порт должен быть открыт извне);
  - **Cloudflare DNS API** — без открытия портов (на выбор: API Token с правами Zone.DNS: Edit, либо Global API Key + email аккаунта);
- e-mail для Let's Encrypt.

Домены и параметры БД установщик кладёт во временный `data/install.json`, и
PHP-мастер подставляет их сам — повторно вводить не нужно (после установки файл
удаляется).

После установки откройте `https://<домен>/admin/`, пройдите мастер (данные БД
печатает установщик), задайте URL панели + API-токен и секрет вебхука, затем
пропишите `https://<домен>/webhook.php` в `.env` панели Remnawave.

### Вариант 3. Отдельный сервер на Docker (вручную)

Образ универсальный, поэтому отдельный сервер можно поднять и на Docker. `install.sh`
этот путь не ставит — настройка ручная:

- запустите контейнер своим `docker-compose` (за основу — `docker-compose.example.yml`),
  **без** подключения к docker-сети панели;
- TLS и домен зеркала — на внешнем reverse-proxy перед контейнером (nginx/Caddy на хосте);
- панель укажите по публичному `https://`-адресу, а не по внутреннему имени контейнера;
- откройте `https://<домен>/admin/` и в мастере выберите режим **«зеркало»**, задав
  origin-домен подписки.

Подходит, если хочется единообразного Docker-развёртывания. Для типичного отдельного
сервера проще «Вариант 2» (файлами) — он сам ставит nginx + TLS.

### Сертификат

Один домен — один сертификат, без wildcard. Способ на выбор при установке:
HTTP-01 (`certbot --webroot`, по 80 порту) либо Cloudflare DNS
(`certbot --dns-cloudflare`, без открытия портов). Автопродление настраивает сам
certbot (systemd-таймер); при продлении сертификата nginx автоматически
перезагружается, чтобы подхватить новый (`--deploy-hook "systemctl reload nginx"`).

## Установка на шаред-хостинг (FastPanel и другие панели)

Прослойка — обычное PHP-приложение без демонов и cron, поэтому работает и на
шаред-хостинге с панелью управления (FastPanel, ISPmanager, Hestia, cPanel и т.п.).
Нужен PHP 8.1+ (`pdo_sqlite`/`pdo_mysql`, `curl`, `mbstring`) и Apache с `.htaccess`.

Создайте сайт на домене зеркала с TLS, залейте файлы репозитория в корень и откройте
`https://<домен>/admin/` — мастер спросит остальное. Важное для прослойки:

- Скрытый `.htaccess` должен загрузиться (файловые менеджеры часто прячут dot-файлы) —
  без него не закроются служебные пути.
- Каталог `data/` — доступен PHP на запись (обычно так и есть).
- После мастера пропишите `https://<домен>/webhook.php` в `.env` панели.
- Проверьте, что `/config.php`, `/data/`, `/lib/` отдают 403/404; иначе включите
  `.htaccess` (`AllowOverride`) в панели.

Обновляется прямо из админки («Обслуживание → Обновление») — git на хостинге не нужен.

## О скрипте установки (стек и ресурсы)

**Стек:** актуальный nginx (из nginx.org) + PHP-FPM (режим `ondemand`) + SQLite (по умолчанию) или MySQL/MariaDB. Отдельный сервер БД для SQLite не нужен.

В простое почти не ест ресурсы (`pm=ondemand` поднимает воркеры только на запрос) —
хватает слабого VPS (1 vCPU / 512 МБ–1 ГБ). Под нагрузкой каждый запрос подписки
занимает один воркер на время проксирования; дефолтных 8 хватает на десятки
запросов/сек.

SQLite комфортна примерно до 1–2 тыс. пользователей. Узкое место — высокая
одновременная запись: если упрётесь, переходите на MySQL/MariaDB (вкладка «Миграция
БД»). Логи режутся автоматически, поэтому файл БД не разрастается бесконтрольно.

## SQLite или MySQL/MariaDB — что выбрать

| | SQLite (по умолчанию) | MySQL / MariaDB |
|---|---|---|
| Установка | ничего — файл, встроено в PHP | отдельный сервер БД (`apt install mariadb-server`) |
| RAM в простое | ~0 (внутри процесса PHP) | ~80–150 МБ постоянно (демон БД) |
| Одновременная запись | сериализуется: один писатель за раз (WAL смягчает) | много писателей параллельно |
| Чтение | очень быстрое | быстрое |
| Бэкап | копия файла `data/submw.sqlite` | `mysqldump` |
| Подходящая нагрузка | малый/средний сервис (ориентир — до ~1–2 тыс. пользователей) | крупный сервис, высокая плотная запись |
| Когда брать | по умолчанию: проще, легче, без зависимостей | если упёрлись в одновременную запись или большой объём |

Сменить базу можно в любой момент из админки — вкладка «Миграция БД» (в обе стороны).

## Смена БД на лету (SQLite ↔ MySQL)

Вкладка **«Миграция БД»** переносит все таблицы в другую базу и переключает прослойку
на неё — в обе стороны (SQLite ↔ MySQL). Перед миграцией сделайте бэкап; `config.php`
обновляется сам.

## Обновление прослойки

**Через админку** («Обслуживание → Обновление»): при первом заходе нажмите «Отметить
текущую версию». Дальше прослойка сама проверяет ветку и подсвечивает пункт меню,
когда выходят новые версии; кнопка «Обновить» тянет только изменённые файлы, с
бэкапом и откатом. `config.php`, `.git` и `.backups/` не перезаписываются.

**В Docker** обновление идёт через образ:

```bash
cd /opt/remnawave
docker compose pull && docker compose up -d
```

Тег образа = ветка (`latest` — стабильный, `dev` — тестовый). Перед обновлением
проверьте тег в `docker-compose.yml` — `pull` тянет именно его. Данные в volume не
теряются.

**Вручную с сервера** (установка из git):

```bash
cd /opt/remnawave-subscription-middleware
git fetch origin && git reset --hard origin/main
sudo systemctl reload php*-fpm 2>/dev/null || true
```

После — отметьте текущую версию в админке.

## Может ли прослойка навредить панели и пользователям

**По умолчанию прослойка панель не изменяет** — только читает (пользователи,
устройства, брендинг) и проксирует подписки. В живую панель пишут лишь две вещи:

- **Грейс-сквад** (по умолчанию выключен). При включении на событие `user.expired`
  меняет у пользователя сквады, лимиты и дату истечения, а при оплате возвращает
  обратно. Самый рискованный компонент: снимок исходного состояния хранится в таблице
  `grace_users` — без неё корректный возврат невозможен. Включайте после проверки на
  тестовом пользователе и держите бэкап.
- **Удаление устройства (HWID)** — только по ручному клику в админке.

Кроме того: API-токен открывает доступ к API панели — держите его в секрете и
ограничьте доступ к админке. С **Remnawave 2.8.0** токен можно выпустить с
ограниченными правами — рекомендуем дать прослойке только нужный минимум, а не полный
доступ.

## Требования

- Сервер на Ubuntu 22.04+/Debian 12+ (root/sudo). Подходит слабый VPS — или
  шаред-хостинг с PHP 8.1+ (см. раздел про шаред-хостинг).
- БД — SQLite (файл), отдельный сервер БД не нужен.
- Домен в Cloudflare — только если выбираете сертификат через Cloudflare DNS (для HTTP-01 не требуется).
- Доступ к панели Remnawave: URL и API-токен (для админки), секрет вебхука.

## Совместимость с версиями панели

Поддерживаются **Remnawave 2.7.4+ и 3.x** — одна и та же версия прослойки работает
с обеими, переключать ничего не нужно.

Панель 3.0 убрала у пользователя поле `uuid` и перевела все пути и тела запросов на
числовой `id`. Прослойка определяет это по самому ответу панели: есть `uuid` —
работает по нему, нет — по `id`. Порядок обновления любой: можно сначала обновить
панель, можно прослойку.

Записи пользователей, ушедших в грейс **до** обновления панели, чинятся сами при
первом же обращении — сохранённый идентификатор перезапрашивается по `shortUuid`.
Пересчитать всё разом можно кнопкой «Обновить идентификаторы» во вкладке «Подмена».

Версия панели видна в шапке админки рядом с версией прослойки и в разделе
«Система» → «Панель» (источник — `GET /api/system/metadata`).

Ещё два момента по панели 3.0:

- настройки подписки `profileTitle`, `profileUpdateInterval`, `supportLink`,
  `isProfileWebpageUrlEnabled`, `happAnnounce`, `happRouting` переехали в кастомные
  заголовки панели (`profile-title`, `profile-update-interval`, `support-url`,
  `profile-web-page-url`, `announce`, `routing`) и теперь уходят **всем** клиентам,
  а не только Happ. На вкладке «Заголовки» они появятся в колонке «из панели»;
- панель больше не сжимает тело ответа — сжатие должен делать реверс-прокси.
  В конфиге, который печатает `install.sh`, `gzip on` уже включён; если ставили
  вручную, проверьте, что `gzip_types` покрывает `text/plain` и yaml.
